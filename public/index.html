How it works

The bank generates the evidence.
The auditor reads it.

Nothing is collected by hand. Bank code cannot write to the audit log directly — it hands the event to the engine, and the engine decides what it means.

01

The Demo Bank acts

A customer logs in, deposits, withdraws, transfers, pays a bill, changes a password. An admin edits a user. Every one of these is an action worth remembering.

02

The Audit Engine judges

It files the event under a compliance category, scores it 0–100, and escalates it on context. One failed login is a typo. Five is an attack.

03

The Auditor investigates

Alerts arrive already triaged. The auditor works the queue, writes findings, and closes the case — and their own work is audited too.

Security

Even the auditors are watched

An audit system that its own staff can quietly edit is worth nothing. Admin and auditor actions are recorded exactly like a customer's.

  • Passwords hashed with bcrypt. Never stored, never recoverable, not even by an administrator.

  • Every query is a prepared statement. There is no string-concatenated SQL anywhere in the codebase.

  • Refused access is still evidence. A customer who pokes at the auditor's API is turned away — and logged as a critical event.

  • Brute force locks the door. Five wrong passwords and the account closes itself, with a critical alert already waiting.

About us

Built to answer one question

"Who did this, and when?" It sounds simple. In most systems it is not, because the logging was an afterthought — bolted on late, easy to bypass, and impossible to search when it matters.

Sentinel Bank was built the other way around. The audit trail came first, and the bank was built on top of it. The result is a system where the honest answer to "could someone have done this without us knowing?" is simply no.

It brings together the things a real financial institution needs in one place: web development, database design, access control, fraud detection, security monitoring and the audit process itself.

Questions

The things people ask first

Is any of this real money? +

No. Sentinel Bank is a demonstration system. The accounts, the balances and the transfers are all simulated — but the audit trail, the risk scoring and the fraud detection running behind them are real code doing real work.

Can an administrator quietly delete an audit record? +

No. There is no endpoint in the entire system that deletes an audit event — not for an admin, not for anyone. Deleting a user is possible, but the act of deleting them is written to the log first, and the record of everything they ever did survives them.

What happens if a fraud rule is wrong? +

It gets closed as a false positive, with the auditor's reasoning attached — which is how a real security team works. If the rule is wrong too often, an administrator retunes its threshold from the admin panel and the engine behaves differently on the very next transaction.

Who can see the audit log? +

Only auditors and administrators. A customer who goes looking for it is turned away — and the attempt is recorded as a critical event, which is rather the point.
